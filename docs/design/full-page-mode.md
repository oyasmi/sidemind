# SideMind 全页面模式设计

状态：第一版已实现。入口为侧边栏顶栏的“Open full page”；两种模式共用 `sidebar.html` 和业务逻辑。

## 目标与范围

为需要长时间、多轮交互的用户提供完整浏览器标签页。侧边栏继续承担浏览网页时的快速提问；全页面提供常驻历史导航、长对话定位和对话资料查看。两种模式使用相同的会话、消息、草稿、附件和设置。

第一版不支持在请求准备、生成回答或停止清理期间切换模式。请求继续由发起它的页面执行，不迁移到 Service Worker，不增加后台生成服务。

## Open WebUI 参考结论

本次参考官方文档及源码快照 `f7ac7ee10962ddec0017f5c29b6740d9b9c5faca`。以下是对其结构的观察；后续 SideMind 方案是针对本项目的设计取舍。

- [Sidebar.svelte](https://github.com/open-webui/open-webui/blob/f7ac7ee10962ddec0017f5c29b6740d9b9c5faca/src/lib/components/layout/Sidebar.svelte)：新建、搜索、历史集中在常驻导航，支持收起，并按日期组织会话。SideMind 采用这个组织方式，首版保持日期分组和现有历史操作。
- [Navbar.svelte](https://github.com/open-webui/open-webui/blob/f7ac7ee10962ddec0017f5c29b6740d9b9c5faca/src/lib/components/chat/Navbar.svelte)：当前会话标题和会话操作放在主区顶栏。SideMind 顶栏只保留标题、辅助面板、模式切换与更多操作。
- [ChatControls.svelte](https://github.com/open-webui/open-webui/blob/f7ac7ee10962ddec0017f5c29b6740d9b9c5faca/src/lib/components/chat/ChatControls.svelte)：辅助区域按需打开，包含 Controls、Files、Overview 等入口。SideMind 缩减为“大纲 / 附件”，模型、角色选择继续留在输入框内。
- [Overview.svelte](https://github.com/open-webui/open-webui/blob/f7ac7ee10962ddec0017f5c29b6740d9b9c5faca/src/lib/components/chat/Overview.svelte)：会话总览使用图形库。SideMind 的首版大纲直接由用户消息生成文字列表，点击定位，不新增分支数据或图形依赖。
- [MessageInput.svelte](https://github.com/open-webui/open-webui/blob/f7ac7ee10962ddec0017f5c29b6740d9b9c5faca/src/lib/components/chat/MessageInput.svelte)：输入区域有独立的宽度控制和附加能力。SideMind 提供更宽、更适合长提示词的输入区，复用现有模型、角色和附件操作。

Open WebUI 是功能广泛的自托管平台。SideMind 的这次迭代聚焦双模式和长会话体验，继续使用原生 HTML/CSS/JavaScript。参考其信息架构，界面和实现独立编写。

官方功能介绍：[Chat & Conversations](https://docs.openwebui.com/features/chat-conversations/)。

## 页面结构

全页面入口为扩展内页面，例如 `chrome-extension://<id>/sidebar/sidebar.html?view=workspace#session=<id>`。模式由明确参数决定；响应式宽度只决定导航、辅助面板如何显示，不把拉宽的侧边栏自动识别成工作台。

### 左侧：会话导航

- 默认宽度 248px，可以收起；第一版使用固定宽度，不加入拖拽调整。
- 上方是 SideMind、新建对话和搜索框。
- 历史按最近更新时间分为今天、昨天、过去七天和更早，不显示空分组。
- 搜索复用现有标题与正文搜索；结果提供匹配摘要，点击进入对话。
- 会话行展示标题、当前选中状态和草稿提示；重命名、删除、导出放在更多菜单。
- 底部放设置入口，不添加账号区域。

### 中间：对话与输入

- 顶栏展示会话标题；右侧是“对话面板”“回到侧边栏”和更多操作。
- 正文默认最大阅读宽度 820px；大屏两侧留出余量，代码、表格在该区域内独立横向滚动。
- 用户消息使用轻量底色，助手回答采用开放排版。延续当前暖灰背景、橙色操作色和深色主题。
- 消息操作复用复制、编辑、重新生成及已有协议限制；不因进入全页面放开受限的服务端会话操作。
- 底部输入区与正文对齐，长文本可以增长到约屏幕高度的 30%，之后在输入框内滚动。
- 输入区继续展示模型、服务商、角色、附件和发送/停止按钮，避免在顶栏重复模型选择。
- 有消息后页面以阅读为中心；新会话时输入区和已有建议提示在主区居中，不新增功能卡片首页。
- 阅读旧消息时不强制滚动到底部；继续使用“查看最新”入口。

### 右侧：按需辅助面板

面板默认关闭，通过顶栏或附件入口打开，默认宽度 304px。一次只显示一个标签：

1. **大纲**：按顺序列出用户提问，截取首个非空文本作为标题；只有附件的消息显示附件名。点击定位原消息，不调用模型生成摘要。
2. **附件**：列出本会话历史和当前草稿引用的文件，按附件 ID 去重；保留原始消息入口。已有图片预览能力直接复用，其他格式先提供名称、类型、下载和定位。

“附件列表”只帮助查看与定位，不改变请求携带附件的规则。仍由现有 `requestHistory()` 决定最新目标用户轮次发送原件、较早附件作为文本记录。

第一版不加入通用文档编辑器、HTML 执行预览或参数面板。大纲是现有历史的投影，附件区是现有引用的投影，两者都不创建新的内容副本。

### 响应式规则

| 页面可用宽度 | 布局 |
| --- | --- |
| ≥1280px | 左侧会话导航常驻；打开右侧面板时与主区并排 |
| 900–1279px | 会话导航常驻；右侧面板以抽屉覆盖，保留主区阅读宽度 |
| <900px | 会话导航折叠为抽屉；左右抽屉互斥打开 |

辅助区关闭时主区重新获得空间。导航和辅助面板分别记忆展开状态。布局不依赖浏览器 Fullscreen API。

## 双向切换

### 允许切换的状态

- 已完成、空闲：可切换。
- 请求准备、附件仍在处理、流式或非流式请求进行中、停止后仍在清理：禁用切换按钮，并显示具体原因。
- 用户需要提前切换时，先点现有“停止”，清理和保存成功后再切换。
- 不自动停止，不自动排队切换，也不重发请求。

### 侧边栏 → 全页面

1. 捕获当前会话 ID、输入框草稿及附件引用、阅读锚点。
2. 主动刷新草稿与消息保存，等待写入队列结束。失败则留在原页面，使用现有保存失败提示。
3. 通过后台的小型导航协调器，复用同一浏览器窗口已有的工作台标签页，或创建一个。复用的标签页若正忙，不强行改换其会话。
4. 目标页面根据明确的会话 ID 读取共享记录，恢复草稿和阅读锚点，并确认已准备好。
5. 确认目标已准备后收起侧边栏。Chrome 141+ 可使用 `sidePanel.close()`；旧版保留侧边栏并提示已在工作台打开，不通过禁用再启用面板模拟关闭。

新页面加载或恢复失败时，原页面继续可用。不会因为读取中的临时空状态创建额外会话。

### 全页面 → 侧边栏

打开侧边栏的调用由按钮点击直接触发，以保留 Chrome 要求的用户手势；切换目标在会话和草稿保存后才消费。侧边栏准备完成前，工作台保持可用。目标就绪后，优先回到进入工作台前的网页标签；原网页已不存在时，侧边栏仍在当前窗口打开。

工作台标签页保留，便于稍后继续；不自动关闭用户标签页。再次进入时复用它。

导航协调器只处理打开/定位标签页、目标会话和目标就绪消息，不持有生成请求。传递数据以 ID 和阅读锚点为主，不在 URL 中放正文或密钥。

## 一致性与并发规则

### 同一份内容

- 消息和标题继续使用 `chrome.storage.local` 的 `session:<id>`；复用现有版本与冲突合并，不增加 workspace 会话表。
- 草稿仍按会话保存，补充存储事件处理。没有本地待保存输入时可直接接纳外部草稿；有本地编辑时保留输入并提供恢复外部草稿的入口，不静默覆盖。
- 附件原件继续放在同一扩展源的 IndexedDB，仅保存引用；两个模式都参与现有附件引用保护与清理。
- `message.protocol`、推理摘要、模型信息和生成结果原样保留，不能只同步渲染后的文字。
- 配置沿用现有同步方式，不在本次迭代改变模型和角色设置的作用范围。

### 各页面自己的浏览状态

各页面可独立查看不同会话。页面内切换会话不强制另一个页面跟着跳转；“切换模式”按钮则明确携带当前会话 ID。

全局保存的 `currentSessionId` 只作为未指定目标时的恢复默认值，不能承担页面间导航指令。阅读位置使用消息 ID 与相对偏移，不共用两个布局的绝对 `scrollTop`。

### 最小并发保护

用户可能保留两个入口或打开多个窗口，所以仍需要限制同一会话只能有一个请求。把现有服务端会话的 Web Lock 保护扩展到所有生成，锁持有至清理完成。另一个页面可以查看已保存内容，但不能同时发送、编辑、重新生成或删除正在生成的会话；显示“此对话正在另一个页面生成”。不同会话不相互阻塞。

生成期的另一页面只保证看到已保存的进度或结果，不承诺逐字镜像；没有生成接管能力。操作时获取不到会话锁就提示稍后重试，不引入心跳机制、任务队列或全局编辑接管。不要用普通存储布尔值作为原子锁；页面关闭后 Web Lock 会释放，已保存的未完成回答应呈现中断状态。

已有选中文字导入使用窗口级的 `selection:<windowId>`。双页面需要明确把导入交给侧边栏消费，再通过共享草稿进入工作台，避免两个页面同时导入或删掉对方尚未处理的选择。

## 实现边界

建议继续使用一份页面结构、一份消息渲染与业务逻辑，通过 `data-view="sidebar|workspace"` 和少量布局分支呈现两种外壳。把已有历史列表改成可复用的渲染目标：侧边栏放在原对话框中，全页面放在常驻导航中，避免两个历史组件各写一遍。

新增工作控制在以下范围：

- `sidebar.html`：导航区域、辅助面板、切换按钮；保留原有消息和输入节点。
- `workspace.css`：工作台 Grid、宽屏排版与抽屉断点；复用共享主题变量。
- `sidebar.js`：模式初始化、明确会话路由、草稿外部更新、删除传播、所有生成的会话锁和派生大纲/附件列表。
- `background.js`：轻量导航消息与工作台标签页复用。

不强行把整个 `sidebar.js` 拆成新架构，也不复制成 `workspace.js`。没有网络或后台生成能力变化时，不需要改动 API 适配器。

## 验收重点

1. 双向切换后消息、推理、协议记录、草稿和附件引用一致；阅读锚点合理恢复。
2. 保存失败或目标页面加载失败时，原内容仍可继续操作。
3. 准备、生成、停止清理阶段不能切换；停止后允许切换，部分回答保存正确。
4. 两个入口并存时，重命名、编辑、删除及时更新；正在查看的已删除会话不会被旧页面保存复活。
5. 同一会话的两个发送竞争只产生一个请求；不同会话正常使用。
6. 草稿有冲突时输入不被覆盖；选中文字只导入一次。
7. 工作台重复打开复用已有页面；重载和浏览器前进后退能恢复明确会话。
8. 在 1440px、1024px、768px 与原有窄侧边栏检查布局；抽屉、键盘、IME 和深色主题正常。
9. 大纲和附件区不改变请求历史与原件发送策略。

## 实施顺序

先完成双模式外壳、保存后切换和存储一致性；再接常驻历史导航、大纲与附件列表；最后覆盖模式切换和双页面回归。第一版以这套范围交付，不依赖生成任务迁移。
